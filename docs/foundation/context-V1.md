## V1 — EUR/USD BUY Entry Notification System

We are going to build a **rules-based EUR/USD trade-entry notification tool**. Its job is simple:

> **Watch EUR/USD continuously during the defined trading window, detect a BUY setup based on Ahmad’s PDF rules, calculate the proposed entry information, and send an email notification so the trader can manually place a Buy Limit order in Exness.**

The system will **not execute trades** and will **not manage trades after entry**.

The strategy itself comes from the four-part confluence described in the PDF: trend, pullback, RSI momentum, and bullish price-action confirmation.    

---

# 1. What exactly are we building?

### Product name for now

**EUR/USD BUY Entry Alert — V1**

### Core purpose

The system replaces the trader manually watching charts for the setup.

Instead of:

> Open chart → check 50 EMA → check 200 EMA → wait for pullback → check RSI → inspect candle → decide entry

the system does:

> Market data → calculate indicators → evaluate rules → detect setup → generate entry data → send email.

The trader then manually enters that information into Exness.

Exness's order interface supports a limit-order price field, and Exness documents Buy Limit as an order used to open a long position at a price below the current market price. ([Exness][1])

# 3. The actual strategy V1 will implement

The PDF defines four conditions that need to align before entering. 

For V1, we translate that into a **BUY-only deterministic pipeline**.

## Condition 1 — Bullish trend

The system checks:

```text
50 EMA > 200 EMA
AND
Current price > 50 EMA
AND
Current price > 200 EMA
```

This means the market is considered to be in the bullish trend condition described in the PDF. 

Example:

```text
50 EMA  = 1.13620
200 EMA = 1.12980
Price   = 1.13710
```

Then:

```text
1.13620 > 1.12980 → PASS
1.13710 > 1.13620 → PASS
1.13710 > 1.12980 → PASS
```

So the trend condition passes.

---

# 4. Condition 2 — Pullback

After confirming the bullish trend, the system waits for the price to come back toward the **50 EMA / support area**.

The PDF says the BUY setup should wait for price to drop/touch the 50 EMA or support. 

Conceptually:

```text
Uptrend
   ↓
Price moves higher
   ↓
Price pulls back
   ↓
Price approaches/touches 50 EMA
   ↓
Potential BUY area
```

This is important because we are not simply buying whenever:

```text
50 EMA > 200 EMA
```

The system needs the **pullback** as well.

### Important implementation decision

Before coding the strategy, we need to make the pullback condition completely mechanical.

For example, we need to decide whether:

```text
Candle LOW touches 50 EMA
```

is enough, or whether:

```text
Candle CLOSE is within X pips of 50 EMA
```

is required.

The PDF does not define that tolerance precisely, so this must be specified before the backtest rather than guessed. 

---

# 5. Condition 3 — RSI confirmation

V1 uses:

```text
RSI(14)
```

The PDF describes bullish momentum confirmation as RSI recovering from oversold, crossing above 30, or being above 50. 

So our initial BUY logic will look for something such as:

```text
RSI bullish condition = TRUE
```

But again, we need to convert the PDF's alternatives into exact code.

For example, possible conditions are:

```text
RSI crosses above 30
OR
RSI crosses above 50
OR
RSI is recovering from an oversold region
```

We should not casually choose one without testing because each definition can produce a different number of signals.

---

# 6. Condition 4 — Bullish price action

The final confirmation comes from the candle.

The PDF gives:

```text
Bullish Engulfing
OR
Bullish Pin Bar / Hammer
```

at support / the pullback area. 

Therefore the system checks:

```text
Bullish candle confirmation = TRUE
```

Example:

```text
Price pulls back to 50 EMA
        ↓
RSI becomes bullish
        ↓
Bullish pin bar forms
        ↓
BUY setup candidate
```

---

# 7. All four conditions must align

The main V1 signal engine becomes:

```text
IF
    bullish trend
AND
    pullback to 50 EMA/support
AND
    bullish RSI confirmation
AND
    bullish candle confirmation
THEN
    BUY SIGNAL
```

This is the core idea of the PDF's confluence formula. 

So we are **not building an AI that randomly predicts EUR/USD**.

We are building a **deterministic rules engine** that asks:

> "Does the current market state satisfy the defined BUY setup?"

# 10. Maximum 3 notifications per day

The system will have a hard daily limit:

```text
MAX = 3 BUY alerts/day
```

But this does **not** mean:

> "Generate exactly three signals every day."

It means:

```text
0 valid setups → 0 emails
1 valid setup → 1 email
2 valid setups → 2 emails
3 valid setups → 3 emails
4+ valid setups → maximum 3
```

That distinction is important.

A genuine strategy should be allowed to produce **zero signals** on a day when the conditions do not occur.

We also need a deterministic rule for the case where more than three valid setups occur, such as chronological first-three or another pre-defined selection mechanism. That rule should be fixed before testing.

# 15. One important issue: lot calculation

There is one thing we need to resolve before implementation.

You want V1 to provide:

```text
Entry price
+
Lots
```

"according to the PDF."

But the PDF's risk-management section derives position sizing from risk and stop-loss distance. 

At the same time, we have defined V1 as having **no SL management**.

Those are not exactly the same thing.

So we need to decide one of these implementations before coding:

### Option A — Use the PDF's risk formula internally

The system can calculate a reference risk/SL distance purely for **lot-size calculation**, while still not sending or executing an SL.

That would preserve the PDF's position-sizing methodology.

### Option B — Use a fixed/configurable lot size

For example:

```text
Configured volume = 0.10 lots
```

and the strategy generates the entry signal independently.

This makes V1 simpler but means the lot is not dynamically derived from the PDF risk formula.

**This is the one technical requirement I would lock down before implementation.**

# 22. Why logging matters

The first objective is not simply:

> "Make an email arrive."

The actual objective is:

> **Verify that the computer is interpreting Ahmad's strategy exactly as intended.**

For example, we might discover:

```text

2,140 potential setups

30m:
730 potential setups

1H:
180 potential setups
```

or find that a particular definition of RSI generates far too many alerts.

Without logging, we won't know why.

# 23. Backtesting is part of V1 development

Before relying on live alerts, we need historical testing.

We should test:

```text
15m
30m
1H
```

with the same deterministic rules.

The testing should answer things such as:

```text
How many signals?
How many per day?
How often does price move favorably afterward?
How much adverse movement occurs?
How quickly does price invalidate the setup?
What happens across different market periods?
```

Because V1 doesn't define automated exits, we should **not casually call the result a traditional "win rate"** unless we first define exactly what constitutes a win/loss.

For example, we could evaluate:

```text
Return after N candles
Maximum favorable excursion
Maximum adverse excursion
Whether price moves X pips upward before Y pips downward
Signal frequency
```

That gives us meaningful evidence without inventing an exit strategy that isn't in the product.

# 24. Exact rules must be made mechanical

This is probably the most important development step.

The PDF explains the strategy conceptually, but some details are still open.

Before the backtest we need exact definitions for:

### Pullback

What exactly counts?

```text
wick touches EMA?
close touches EMA?
within 2 pips?
within 5 pips?
```

### RSI

Which condition triggers?

```text
cross above 30?
cross above 50?
recovery from oversold?
one of several conditions?
```

### Pin bar

What exact candle geometry?

For example:

```text
lower wick >= X% of candle
body <= Y%
close in upper Z% of range
```

### Bullish engulfing

What exact definition?

```text
previous candle bearish?
current candle body completely engulfs previous body?
does wick matter?
```

### Entry

When is the signal generated?

```text
at confirmation candle close?
next candle open?
specific pullback price?
50 EMA?
```

These are not small implementation details. They can materially change the number and characteristics of signals.

# 26. Duplicate-alert protection

This is another feature we should include from day one.

Suppose the same setup remains true for several checks.

We don't want:

```text
14:30 → email
14:31 → email
14:32 → email
14:33 → email
14:34 → email
```

for the same setup.

So V1 needs **signal deduplication**.

A signal should have a unique identity, for example:

```text
EURUSD + timeframe + confirmation candle timestamp
```

Once that setup has produced an alert:

```text
don't send another alert for the same setup
```

until a new setup is formed.

# 34. Final V1 definition

So I would define **V1** like this:

> **A backend-based EUR/USD BUY-only trade-entry notification system that continuously monitors EUR/USD during 8 AM–11 PM Dubai time, evaluates the 50 EMA / 200 EMA trend, pullback to the 50 EMA or support, RSI(14) bullish confirmation, and bullish candlestick confirmation according to Ahmad's strategy, and when all required conditions are satisfied, generates a BUY LIMIT entry with the required price and volume information and sends it to the trader by email. The trader manually enters the information into Exness. V1 has a maximum of three alerts per day, supports 15m/30m/1H for testing, logs every decision, and excludes selling, broker API execution, stop-loss/take-profit management, position management, and AI-driven decision making.**

The PDF's own summary describes the strategy as **trend confirmed + pullback to value area + RSI momentum alignment + candlestick confirmation + risk managed**; for our V1, the first four components become the signal engine, while trade-management automation remains outside scope.
